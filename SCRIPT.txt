RECLAIMIFY, demo script
Five beats, about five minutes. Every number here is in development/METRICS.md.

BEFORE YOU RECORD
  cd development
  python run.py dry          # 13 checks, network cut. must be 13 of 13.
  python run.py room         # writes artifacts/case_room.html
  python run.py console      # writes artifacts/dashboard.html
  open artifacts/case_room.html and artifacts/dashboard.html

  Pull the network cable, or turn wifi off. The page is one file and the demo

  The console is for beats 1 and 5, where the argument is about the whole pile.


-------------------------------------------------------------------------------
BEAT 1  THE PILE IS MOSTLY GOOD CUSTOMERS, AND NOBODY LOOKS AT IT   (45 sec)
-------------------------------------------------------------------------------
On screen: nothing yet, or the terminal.

Say:

  A fraud system blocks an order. What happens next is nothing. The customer
  assumes their bank declined them and buys somewhere else. No complaint, no
  dispute, no refund, and no row anywhere saying a good customer was turned
  away.

  Now compare that to letting fraud through: a chargeback arrives, money is
  clawed back, there is a fee and a dispute record, and somebody's number
  moves.

  One side of the trade is measured and the other side is invisible. So
  blocking more always looks like an improvement, and the threshold ratchets
  one way forever. About a third of merchants do not track their
  false-decline rate at all, which is less negligence than an absence of
  anything to track.

  In our data, the risk stack blocked 8,265 orders. 6,346 of them were good
  customers. That is Rs 44 crore of revenue refused against Rs 11 crore of
  fraud correctly stopped, a ratio of four to one, and nothing in the stack
  ever revisits it.

  This is an appeals court for that pile.

Do NOT say: "we recover crores". The recovery number comes later, next to the
fraud number, and never on its own.


-------------------------------------------------------------------------------
BEAT 2  RELEASE ONE, LIVE, WITH ITS VERDICT                          (90 sec)
-------------------------------------------------------------------------------
On screen: case room, first case in the list.
  pay_5E72cODtQrmZkn, Aurum Jewels, Rs 5,15,681, UPI

Say, pointing at the left column:

  This is what the merchant could see. New device. Basket four and a half
  standard deviations above this merchant's norm. A pincode with a bad return
  index. It scored 0.509 against a threshold of 0.38, so it was blocked for
  amount anomaly. Every one of those signals is a correct description of
  unusual behaviour and a wrong inference about intent.

Then the right column:

  This is what only the payment network can see. Seventy-five prior orders.
  Fifteen hundred days of tenure. A 96% clean completion rate. The merchant
  cannot buy this view at any price, because it is not their data.

Then the verdict:

  Probability the block was correct: 0.003. Overturn.

  The note underneath was written by a model, and the badge says which one.
  Every number in it was checked against the evidence on this page before it
  was shown. If the model writes a figure that is not derivable from the
  evidence, the note is rejected and rewritten.

  What the model did not do is decide. The action came from an
  expected-value rule, before the model saw anything. Three tests enforce
  that: the tools it can reach take no free text, the extraction schema has
  no field for a decision, and the verdict is handed a decision that was
  already made.

Point at the provenance badge explicitly. Say the words "written by".

BEAT 3  UPHOLD THE CLEAN-LOOKING ONE                                 (60 sec)
-------------------------------------------------------------------------------
On screen: pay_0T6ICR8cppsGGD, PharmaNow, Rs 1,195.
  Listed as "A spotless record the system still refuses".

Say:

  The obvious version of this idea is "long clean history means safe". That
  rule loses money, because it is the rule professional abuse is built to
  beat.

  Look at this file: clean rate 1.000. Perfect. Zero disputes, zero returns.
  A model keyed on clean rate releases this immediately.

  It has one prior order spread across seven merchants in under a year. That
  is not a shopping pattern, it is a shape. The system upholds the block at
  0.750, and the answer key says it was right: this one would have come back
  as a return.

  Forty-two percent of the fraudster population in this data are bust-outs
  that deliberately farm a clean record before cashing out. That is a
  parameter in the generator, not an accident. If the demo only showed us
  releasing obviously good customers it would prove nothing. The test is
  whether we refuse someone whose record looks perfect.

If asked "isn't Rs 1,195 a small case": yes, and that is the point. Say so.
The cheap cases are exactly the ones a human queue never reaches, which is
Beat 5.


-------------------------------------------------------------------------------
BEAT 4  AN ABSTENTION                                                (30 sec)
-------------------------------------------------------------------------------
On screen: pay_5sr9UbuKWw8GCM, Aurum Jewels, Rs 2,92,581.
  Listed as "Too thin to judge".

Say:

  Nearly three lakh rupees, and the network file is empty. No prior orders
  anywhere. There is no exculpatory evidence, because there is no record.

  The system does not guess. It asks a question instead, and if no question
  would settle it, it escalates to a person with a written brief.

  It refuses to decide on 15.3% of cases and that number is reported, not
  hidden. A model that produces a confident answer on an empty file is
  lying.

Do not oversell this. Thirty seconds, then move.


-------------------------------------------------------------------------------
BEAT 5  THE FRONTIER, THE ONE WE GOT WRONG, AND THE FOUR NUMBERS
        THAT GOT WORSE                                               (90 sec)
-------------------------------------------------------------------------------
This is the beat that wins or loses it. Do not rush it and do not treat the
last part as a footnote.

On screen: the console, Operating point page. Put your hand on the cap
slider before you start talking. Then switch to the case room for
pay_cHqPoyD6hCHji7, "The most expensive wrong release", and finish on the
console's "How honest is it" page.

Say, first the headline:

  On 1,775 blocked orders the model never trained on: 88.2% of recoverable
  revenue recovered, at 96.3% precision. Rs 7.21 crore recovered, and
  Rs 51.21 lakh of fraud let through. Those two numbers appear together in
  every table in this project. There is no table showing one without the
  other.

  The operating point is not tuned. Releasing is worth money only while the
  probability of being wrong is below margin over one plus margin, which at a
  25% margin is 0.20. That is where we sit.

  [drag the slider left]

  Here is 0.02. Precision goes to 98.6%, which looks better on a slide, and
  recall drops seven points, which is revenue we are choosing not to recover.
  Picking the threshold that flatters the precision column is exactly the
  behaviour this project exists to criticise, so we ship the point where the
  arithmetic stops working rather than the point where the table looks best.

Then the case you got wrong:

  Here is one we released and should not have. Rs 2,11,715. Forty-seven prior
  orders, four years of tenure, 98% clean. Everything says release. The
  customer took delivery and returned it.

  No threshold removes this class. The evidence that exonerates an honest
  atypical buyer is the same evidence. So the operating point prices it
  instead of pretending it away.

Then, deliberately, the differentiator:

  Four numbers moved against us this week and we took all four.

  One. We stopped demoing at the threshold that flattered precision. Moving
  to the honest operating point took precision from 98.6% down to 96.3% and
  roughly doubled the fraud we admit.

  Two. We added a human reviewer baseline, and it beats us. A person
  adjudicating every case reaches Rs 1.36 crore against our Rs 1.29 crore.
  We left the row in.

  Three. We declared where this runs. Inline at checkout it is worth
  Rs 1.29 crore. As a queue that emails people later, breakeven is a 28.6%
  return rate, and below that it costs money.

  Four. We regraded across five generated worlds and found we had been
  quoting a precision range measured at a different operating point. The
  honest range is 92 to 98 percent, not 98 to 99. So "precision is stable" is
  withdrawn.

  Recall is the number that holds: 83 to 90 percent across every world.
  Precision moves six points. Money moves about two-fold. Each of those
  depends on something different, and knowing which is which is the
  difference between a metric and a slide.

Close on:

  We lose to a reviewer case for case. But nobody can afford a reviewer on
  the whole pile. At 10% coverage, which is generous, a human queue recovers
  8.6% of the recoverable revenue. This recovers 88.2%. The gap is not
  intelligence. It is reach.

If you have the console open, that whole closing argument is one table on the
"How honest is it" page. Point at it rather than reciting it.

IF ASKED "DOES IT ACTUALLY RUN, OR IS THAT A MOCKUP"
-------------------------------------------------------------------------------
Open the console, Run the agent page. Edit a number in the JSON, anything, and
hit Adjudicate. Watch the probability and the action change.

  That is the model. The 300 fitted trees and the calibrator are exported into
  the page and evaluated in the browser. The exporter refuses to write them out
  unless the JavaScript reproduces the Python probability on all 1,775 holdout
  cases, and a separate check pulls those functions out of the built page and
  runs them again. Worst disagreement is five times ten to the minus fifteen.

Three edits that land, all verified on the shipped page:

  network_orders_prior 75 -> 1
      OVERTURN becomes STEP_UP. The probability does not move at all, 0.0031
      either way. The evidence gate fired, not the model. Worth saying out
      loud: the system is not less confident, it has decided it does not have
      enough record to act on, which is a different thing.

  network_clean_rate 0.96 -> 0.20 and network_disputes_prior 1 -> 6
      p goes 0.0031 to 0.2317 and the action becomes STEP_UP, ambiguous.
      That is the model, not the gate.

  network_orders_prior -> 1 and amount_inr -> 3000
      ESCALATE instead of STEP_UP. Same thin file, but it is not worth a
      verification exchange on a three thousand rupee order, so it goes to a
      person. The policy spends effort where the money is.

IF THERE IS TIME, OR IF ASKED
-------------------------------------------------------------------------------
Two things that were silently broken, and how we found them. Both had green
tests on top of them. Both were found by looking at real output.

  The citation checker was reading digits out of payment ids, so every
  correctly cited model verdict failed and fell back to a template. "300 of
  300 audit clean" was true and was measuring nothing. Only a live model call
  exposed it.

  The demo screen contained no demo cases. It sliced the first 400 orders by
  date and five of the six demo cases sit past 400. The page looked normal.

A test that passes tells you the code did what the test asked. It does not
tell you the test asked for anything.
