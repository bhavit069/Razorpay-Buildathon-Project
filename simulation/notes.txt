2026-08-26 afternoon - decision system
--------------------------------------
truth vault - the answer key behind one module with two entry points. training
  can only ask about the train split and errors otherwise. scoring sees
  everything. cheating has to be deliberate.

feature store - hands you one blocked order's evidence in three labelled piles:
  what the shop could see, what only the network can see, and bookkeeping.
  switching between "shop only" and "shop plus network" is one argument, so the
  moat comparison can't become two different programs.

model - estimates the chance a block was correct, then a calibration step maps
  those onto a scale where 0.2 means one-in-five. the next layer spends them
  like prices so the scale has to be right.

policy - turns the estimate into one of four actions using arithmetic about
  money rather than a fixed cutoff. release, uphold, ask the customer, hand to a
  person. the same estimate gives different actions on a Rs 500 order and a
  Rs 5,00,000 one.

the policy can't release anything it's more than 20% unsure about, and no
  setting changes that. it falls out of the arithmetic: you earn a quarter of a
  sale but lose the whole basket, so past a certain doubt the sum is negative
  regardless of order size. margin sets the ceiling, not risk appetite. the
  sweep table in the pitch doc runs to 0.5, which an EV rule can't reach.

replay - walks the blocked pile in date order and records every decision. truth
  is joined afterwards, never during. two runs produce identical files.

scorer - joins truth at the end and prices everything. reports recovered and
  fraud admitted side by side, with error bars.

report writer - regenerates METRICS.md. every number the pitch quotes comes out
  of here.

releasing everything makes more gross revenue and still loses money once margin
  is counted properly. strongest single argument for having a policy.

the moat is real but small. measured it at +63% earlier by comparing both models
  at the same cutoff, which was wrong because the shop-only model's raw scores
  sit on a different scale. once both are calibrated and each gets its own
  operating point it's about +5%. the claim that holds isn't the size, it's that
  network evidence releases more orders at higher precision at the same time.
  moving a cutoff can't do both.

three test files - can training see the answer key (no), does signal vanish when
  labels are scrambled (yes, 0.91 to 0.49), can a feature know the future (no,
  3401 checks), does the policy behave, are two replays identical. 33 tests.

bug: a case the model was certain was fraud got sent to "ask the customer"
  instead of "uphold". the thin-file guard was running before the confidence
  check. reordered. keeping a block needs no evidence because the block is
  already there, so the guard only has to protect the release direction.

notebooks - five, generated by a script so their printed output can't drift from
  the code. 00 map, 01 data, 02 the moat three ways, 03 probability to decision,
  04 the six pitch cases.

five of the six showcase cases are in the training half. demoing them means
  demoing on cases the model studied. notebook 04 finds holdout replacements.

the Kolkata case doesn't behave as the pitch says. an 88-order customer with
  three years and a spotless record scores 0.22, too high, so the system
  abstains instead of releasing. real model miss.


2026-08-27 - accuracy pass before pushing
-----------------------------------------
seed check - reran the whole pipeline on five independently generated worlds.
  net contribution lands anywhere between Rs 1.15 cr and Rs 1.87 cr. that spread
  is wider than the confidence interval we report inside a single world, which
  means the rupee numbers are limited by how the world was generated, not by how
  many cases the holdout has. precision is stable at 97.8-99.1%. AUC lift ranges
  +0.043 to +0.072. seed 42, which everything else uses, is the worst of the
  five.
  -> quote precision as a number, quote money as a range.

2026-08-27 later - phase 2, the agent
-------------------------------------
ledger - append-only log where each entry hashes the previous one. rewriting a
  past decision breaks every hash after it, so the file shows tampering. tested
  by editing an entry and checking the chain complains about that exact one.

llm client - one entry point to Claude with a disk cache keyed on the inputs.
  three modes: live calls the API and records the reply, replay serves only from
  cache and errors on a miss, offline falls back to a deterministic template.
  offline output is tagged source="template" and never claims to be model
  output. no API key on this machine so everything currently runs offline.

tools - the only path from the agent to anything that moves money. thin wrappers
  over phase 1, every call logged. none of them takes text as an argument, so
  there's no signature through which generated prose could reach the policy.

verdict writer - model gets the evidence and the decision that was already made,
  writes 3-6 sentences. then every number in the prose is checked against the
  evidence and regenerated if it invented one. 300 of 300 clean on the last run.

  found a bug in that check: amounts print rounded to whole rupees, so a Rs
  641.76 order shows as "642", and the checker rejected it as invented. now
  allows the rounded form of any value.

stepup - two model roles, agent asks and a simulated customer answers, seeded
  from ground truth so honest customers answer and fraudsters evade. a third
  call extracts structured facts. only the facts come back; the model's opinion
  of the conversation is thrown away.

orchestrator - the case loop. adjudicate, decide, maybe verify, write, log.

got the step-up mechanism wrong twice before getting it right:

  first version zeroed the customer's past return count when they agreed to
  prepay. that's falsifying history - prepaying removes FUTURE return risk, it
  doesn't mean the returns never happened.

  second version credited verification as extra prior orders. same mistake in a
  different costume. and it backfired: adding 3 orders to a thin file in the
  same tenure looks like velocity, so two customers who verified successfully
  came out scoring WORSE than before they answered (0.204 -> 0.571).

  the actual fix: verification isn't history and doesn't belong in the features
  at all. it goes to the insufficiency gate, which is asking "can we identify
  this person", and leaves p_bad completely alone. the record didn't change so
  the estimate of the record shouldn't either. tested.

then: only 2 of 75 step-ups resolved anything, because most step-ups come from
  the ambiguous branch where the gate was never the blocker. running a dialogue
  there can't change the outcome. now only insufficiency step-ups get an
  exchange - 4 instead of 75, and both that resolved were correct.

on 300 holdout cases: 151 released at 99.3% correct, 75 upheld, 73 held for
  verification, 1 escalated. all 300 verdicts audit-clean, ledger verifies.

worth noting: upholds are only 56% correct. at cap=0.02 the system is refusing
  a lot of good customers to protect precision on the releases. that's the
  conservative end of the frontier doing what it says.

2026-08-27 evening - hardening
------------------------------
tested the claim the whole two-phase design rests on: that wrapping the decision
  system in an agent doesn't change what it decides. ran both over the same 300
  cases. p_bad identical on all 300 (difference exactly 0.0), and the only two
  action differences are the two step-ups that resolved, which the backtest had
  no way to run. now a permanent test, and demo.py rechecks it every run.

the agent's decisions are now priced by the same grader the backtest uses,
  instead of a separate accounting. as_core_ledger() re-expresses an agent run
  as a phase 1 ledger so core.metrics.grade works on it unchanged. on 300 cases
  at cap=0.02: 151 released, 99.3% precision, Rs 73.06L recovered against
  Rs 1,494 admitted.

escalation briefs. the spec calls escalation a first-class outcome with a
  written brief, but it was just reusing the verdict. now has its own prompt and
  template addressed to a reviewer rather than a merchant: what's being asked,
  what the record shows, what's missing, what would settle it. citation-checked
  like a verdict.

latency percentiles instead of a bare median. p50 0.78ms, p95 1.03ms, max
  4.54ms. that's offline templates; a live run will be dominated by API time.

61 tests.
